# What lives at 0x8040BC18-0x8040F50C (S2 field `range`)

Field agent `range` of session S2 round 4 (2026-11-12), branch `s2/range`, base `s2/integrate` efc1aa8 (runtime code equals 700f72d).
Question: the ownership table (`s2_ownership.tsv`, generated by `game_map.py`) labels 0x8040BC18-0x8040F360 "Heap"; round 3
(`docs/re/appfw.md`, `docs/re/input.md`) found the pad / peripheral library in it, and `docs/agents/opt-matrix.md` owns the matrix library in it.
Settled here per function, with a script that regenerates the table from the DOL and a check with negative controls.

Evidence labels: **P** proven (words of the pinned PAL `game/sys/main.dol`, md5 prefix `a3b73a378782`, recomputed by
`tools/re/range_8040.py --check`), **I** inferred (consistent, not proven by a word), **U** unknown. Names are ours; the only names taken from
the binary are the RTTI class strings. The external decomp was not used.

## 1. Answer

The range holds **six libraries** in this order (140 functions, 14,580 bytes; the function grid equals the ownership table's 140 rows byte for byte):

| range | library | functions | bytes | what it is |
|---|---|---|---|---|
| 0x8040BC18-0x8040BC90 | Task profiling scope | 3 | 120 | constructor stores `OSGetTick()` at +4; only callers are the Task update wrappers 0x8004EA84 / 0x8004EACC / 0x8004EDF0 / 0x8004EE54 |
| **0x8040BC90-0x8040C084** | **Heap** (the only real heap class here) | 9 | 1,012 | RTTI class `Sonicteam::System::Heap`: 8 virtuals + constructor 0x8040C040 |
| **0x8040C084-0x8040E238** | **math library** (matrix, vector, quaternion, a 4-word generator) | 75 | 8,628 | all 18 native owners of the range are here |
| 0x8040E238-0x8040E2A4 | diagnostics | 3 | 108 | `Sonicteam::System::Diagnostics::DefaultDebugListener` virtuals |
| 0x8040E2A4-0x8040E440 | colour utilities | 4 | 412 | ARGB8 helpers + the named-colour static initialiser |
| **0x8040E440-0x8040F50C** | **pad / peripheral devices** | 46 | 4,300 | two device registries, the PeripheralManager, the Pad2Mouse and Pad2Keyboard implementors |

So the "Heap" label is right only for 0x8040BC90-0x8040C084 (1,012 bytes, 7 % of the range). The pad / peripheral library does **not** start
at 0x8040BC18; it starts at **0x8040E440**. The matrix library is the **largest** part (59 % of the bytes) and ends at **0x8040E238**.
`docs/re/appfw.md` line "the 'Heap' label for 0x8040BC18-0x8040F360 is the pad-device library" is therefore corrected: it holds for 0x8040E440-0x8040F50C only.

## 2. Method

`tools/re/range_8040.py` (reads `game/sys/main.dol` and `extract/functions.csv` only):

1. **Grid.** Function starts from `extract/functions.csv`; an entry inside a function that has its own exception-table record is a landing pad
   of it (EA6C inside EA3C, E4BC inside E464, ...). The records are the 12-byte `(start, size, extab)` triplets of the DOL's extab index
   (0x80007628 ff.); their size also corrects `functions.csv` where it split a function (0x8040EA3C is 384 bytes, not 48). Result: 140 functions,
   identical to the 140 ownership rows of the range (addresses and sizes).
2. **Features per function**, from the words: instruction mix (FP load / store / arithmetic share), direct `bl` and tail `b` targets, materialised
   constants (`lis`+`addi` / `ori`, r2 / r13 offsets), every caller in the whole text, code-pointer constants, vtable membership and RTTI class
   (a data word equal to the function is walked back over the slots to the `[RTTI, 0, slots...]` header; the RTTI object's first word points to the
   class-name string), and membership of the `.ctors` table (0x804AB0A0 ff.).
3. **Units.** A unit is a run of functions with one predicate that every member satisfies (table in section 3). Predicates are evidence, not ranges:
   * *heap*: the function is a slot of the `Sonicteam::System::Heap` vtable, or materialises that vtable's address (constructor);
   * *math*: an FP kernel (>= 15 % of its words are FP loads / stores / arithmetic), or a wrapper whose every call target is a kernel or a known
     FP primitive (fixpoint), or one of 8 listed functions with explicit word facts (section 5);
   * *peripheral*: reachable by calls and code-pointer constants from the bring-up 0x8034AD30, the pad hub, the screen test, the three singleton
     getters, or a vtable slot of a `Sonicteam::System::Peripheral::*` class;
   * *diagnostics*: slot of the `DefaultDebugListener` vtable; *colour*: byte-wise code (>= 4 `stb`, no word / half store, no FP, no call);
   * *Task scope*: every caller lies in the Task base 0x8004EA80-0x8004F0FC and there is no vtable.
4. **Boundary claims** (22 claims, all recomputed from the DOL): units tile the range and start / end at function edges; every member
   satisfies its unit predicate; at each library boundary the last function of the earlier unit **fails** the later unit's predicate and the first
   function of the later unit **fails** the earlier one's (exclusion); boundaries inside the math library are static initialisers (`.ctors` entries);
   the five sub-units of the peripheral library are proved by bring-up callee / vtable-class edges; the previous function is the CRI banner function,
   the next function belongs to the resource-loading code; the four RTTI classes hold exactly the 16 virtual functions of the range; the 18 native
   owners are all inside the math library.
5. **Negative control.** `--check --break ADDR` moves the boundary that starts at ADDR one function later; the check must then report a failure
   (section 6).

Why the ownership table got it wrong (P, `game_map.py` read only): the rule `^Sonicteam::System::` maps the Heap, DefaultDebugListener and Pad2*
classes to "game framework"; the *unit* pass then labels every unclassed function whose classed neighbours are both framework and at most 0x2000 bytes
apart (so 0x8040E2A4-0x8040EF60 become "framework, unit"); the math library lies between the Heap (0x8040C040) and the DefaultDebugListener
(0x8040E238), 0x21F8 bytes apart, so the unit pass skipped it and the *callers* pass called it "shared game code (called from several subsystems)".
The `ref_CRI_...` and `ref_Error_initializing_RenderWare_...` names are caller-derived labels, not data.

## 4. The libraries, function by function

The complete table (address, size, library, unit, evidence of every function) is `tools/re/range_8040.tsv`; the notable members:

**Task profiling scope (3).** 0x8040BC18 (`bl OSGetTick`, `stw r3,4(this)`, `stw 0,0(this)`: scope start), 0x8040BC50 (scope end / destructor with the delete flag:
`extsh. r4`, `bl 0x803A1334`), 0x8040BC8C (empty). Name **I**.

**Heap (9).** vtable 0x8056AF2C (slots at 0x8056AF34-0x8056AF50 in the order vf0..vf7): vf7 0x8040BC90 (TotalFree: sums the sizes of the block list), vf6

(the four vtable classes of the range are Heap, DefaultDebugListener, Pad2MouseImplementor, Pad2Keyboard::Implementor).

**Math (75; 18 native owners).** Matrices are 3 rows x 4 floats, rows 0x10 apart (`docs/agents/opt-matrix.md` section 1). Unit A (0x8040C084-0x8040D254, 28 functions):

quaternion / vector kernels (D43C, D5AC, D8C4, D958-DB04), static initialiser DB48. Unit C (0x8040DB7C-0x8040DDC4, 12 functions): the generator DB7C / DBA8 and the 2D vector
kernels DC48-DD8C. Unit D (0x8040DDC4-0x8040E094): 3D vector kernels (sub, scale, add, length, dot, cross; Vec3 names of `native-owners.txt`). Unit E (0x8040E094-0x8040E238): sincosf-based

## 7. game_map patch

`tools/re/range_8040_game_map.patch` (unified diff against the original `game_map.py`; apply from the directory that holds it: `patch -p1 < range_8040_game_map.patch`, or `git apply`).
It adds a `RANGE_RULES` list (6 address ranges -> subsystem) applied to every function after the class / unit passes and before the callers pass, with evidence kind `range`.
Tested on copies of the original (the original script and the notes TSV were not touched): original vs patched run of `game_map.py` over the same skeleton: 141 of 34,037 functions change, 140 in the range
(all 140 now `range`), 1 outside: 0x803269DC (the matrix copy wrapper, `unknown (game-unit)` -> `shared game code`, because its callers now include a range function). New subsystem labels:
"game heap (Sonicteam::System::Heap)" (9), "math library (matrix, vector, quaternion, generator)" (75), "colour utilities (ARGB8 helpers, named colours)" (4),
"pad / peripheral devices (managers, Pad2 implementors)" (46); the Task scope and DefaultDebugListener (6 functions) get the existing "game framework" label.
Field routing suggestion (the coordinator's call): heap -> `heap`, peripheral -> `input`, math and colour -> `-` (opt-matrix's library; unclaimed for S2), framework stays `events`.

## 8. S2 report

Base: `s2/integrate` efc1aa8 (runtime code = 700f72d); `game/sys/main.dol` md5 prefix `a3b73a378782`. No runtime code, matrix owner or build file was changed: documentation, one script, one TSV and one patch file only,
so no build, state.json, PCM or frame gate applies and none was claimed.

**Proven (P).** The six-library split and every boundary of section 3 except the intra-math sub-units; the 16 virtual functions of the range belong to exactly four RTTI classes; the 18 native owners are in the math library;
the grid equals the ownership table's 140 rows; the CRI banner function ends at 0x8040BC18.
**Inferred (I).** Sub-division of the math library into five translation units (a static initialiser ends a unit; the five initialisers are ascending in the `.ctors` table, which fits link order but does not prove the
unit edges); the names Task profiling scope, generator (pseudo-random), keyboard / mouse registry roles, alpha-first colour layout.
**Unknown (U).** Whether the DefaultDebugListener and colour code share a translation unit; the meaning of the 0x38-byte registry slot fields beyond the constants listed; what 0x8040C38C builds (a basis from vectors; one caller 0x8000A67C).

**Corrections for other documents.** `docs/agents/opt-matrix.md` / the contract exclude "0x8040C000-0x8040E100" for opt-matrix: the math library is 0x8040C084-0x8040E238. The contract range wrongly covers
0x8040C000-0x8040C084 (the end of Heap vf0 0x8040BFA8-0x8040C040 and the Heap constructor 0x8040C040; heap field) and misses 0x8040E100-0x8040E238 (the tail of E0FC, and E168, E1D0, E204: sincosf vector helpers and distance wrappers, none native-owned).
`docs/re/appfw.md` section "Findings for other fields" (events): the pad-device library is 0x8040E440-0x8040F50C, not 0x8040BC18-0x8040F360.

**Findings for other fields.** heap: only 9 functions / 1,012 bytes at 0x8040BC90 are the Heap class (vtable and constructor known); `rwalloc`/`heap` need not look elsewhere in the range. input: its four sub-libraries are now bounded (registry 0x80581350 = keyboard side, registry 0x80586924 = mouse side by the bring-up order).

**Owners.** None written. **Claims** added to `s2_claims.tsv`: none (RE only).
