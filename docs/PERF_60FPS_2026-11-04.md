# 60 FPS / 2 ms mission: resolution integrity and baseline (2026-11-04)

Build: `.build/watch` (lifted renderer, non-shipping, Nov 3 16:31). Route: Westopolis gameplay replay
(`westopolis-cpu-spike` tape, `--boot-stage stg0100`), 90 s, fullscreen 1920x1080 @ 60 Hz, RTX 4080, audio on.
Runner `tools/perf/res_ladder.sh`; per-frame work `tools/perf/frame_work.py` (first 15 s = stage load, excluded).
Raw runs: `.build/perf/base1/<WxH>/` (gpu.csv, present.csv, perf.csv, session.json, logs).

## Phase 1: internal resolution is real
- The release game uses the lifted renderer: no EFB and no integer multiplier. The 3D scene is rasterised into
  "view colour" targets of exactly the render size, with 4x MSAA, then resolved at 1x (docs/RESOLUTION_AUDIT.md).
- Runtime evidence, from the renderer's own texture-pool log in each run:

  | asked | view colour target | memory |
  |---|---|---|
  | 854x480 | 853x480, 4x MSAA | 16 MiB |
  | 1280x720 | 1280x720, 4x MSAA | 32 MiB |
  | 1920x1080 | 1920x1080, 4x MSAA | 64 MiB |
  | 2560x1440 | 2560x1440, 4x MSAA | 116 MiB |
  | 3840x2160 | 3840x2160, 4x MSAA | 256 MiB |

  2x per side gives 4x the memory (16 -> 64 -> 256 MiB).
- 853 rather than 854: the renderer takes the height and derives the width from the output's exact 16:9 shape
  (480 * 1920 / 1080 = 853.3).
- Present: the only resampling step is fitting the render size to the 1920x1080 back buffer. Below 1080p that is an
  upsample (bicubic), at 2160p a 2x2 box downsample. At 1080p it is 1:1.
- Fixed-size by design: the glare chain (128-row levels, matching the original's look). It is not a scene target.

## Where 2 ms stands
- 480p: GPU p50 1.55 ms, render thread 0.35 ms, game frame step ~2.6 ms (p90). The game thread is the largest single
  cost already at 480p.
- 1080p and up: the GPU scene pass and the frame-gap / clock behaviour dominate. 2160p repeats (~13 in 75 s) come
  from GPU frames of 12-22 ms.

## Phase 3: where the frame time really goes (1080p, Westopolis replay)

### GPU: clocks, not work
`tools/gpu_clock_sampler.py` (NVML, 10 ms) joined to the GPU trace (`.build/perf/p3b/`):
- 1080p: 4,288 of 5,354 frames ran with the graphics clock at **210 MHz** (idle), GPU frame p50 4.56 ms there. Frames
  that ran at 750-999 MHz: p50 0.79 ms. The card's boost clock is 2,505 MHz.
- 2160p: most frames at 250-499 MHz (p50 5.73 ms); at 500-749 MHz p50 2.95 ms.
- So the 4-6 ms "GPU frame" is the driver keeping the GPU at its lowest clocks because the load is light. The GPU
  work itself is under ~1 ms at 1080p. Not a renderer defect; the driver's power policy decides it (NVIDIA per-app
  "Power management mode", a user setting I did not change).

### Game thread: flat, ~3.8 ms per frame
`tools/perf/sample_threads.py` (external RIP sampler, ~1 kHz, PDB symbols), 55 s of gameplay (`.build/perf/samp2/`):
the game thread is busy 22.8% of wall time = 3.80 ms per 16.67 ms frame.

| part | ms / frame |
|---|---|
| translated game code (fn_* bodies) | 2.11 |
| other runtime (RW driver lookups, scheduler walk, interrupts, clock) | 0.52 |
| audio mixing on the game thread (AX mix, voices, reverb, ADPCM) | 0.44 |
| dispatch / HLE lookups | 0.24 |
| math intrinsics | 0.16 |
| guest memory accessors, native collision, kernel time | ~0.27 |
| render packet build | 0.06 |

No single game function costs more than 0.05 ms per frame (fn_80386BC0, fn_80428044, fn_8041669C lead). There is
no hotspot to remove: the cost is the whole game update spread over thousands of translated functions.

### Render thread
Record + submit p50 0.37-0.41 ms at every size.

### Input latency (controller latch -> displayed vblank, frame_telemetry_report.py)
- 1080p: p50 25.6 ms, p99 45.4 ms. 2160p: p50 20.0 ms, p99 23.6 ms.
- Made of: simulation 3.6 ms, queue hold 0-5 ms (where the game's step falls against the present thread; it depends
  on the boot), render 0.4 ms, GPU 5.3-5.7 ms (at idle clocks), and ~10 ms waiting for the vblank.
- SHADOW_PHASE_LOCK=1 (built, default off, A/B'd 2026-10-31, docs/TIMING_ARCHITECTURE.md 8) pins the hold at ~2 ms.

### Stability
- All sizes ~60 fps. Repeats in 75 s: 0 (480p-1080p baseline), 1 (1440p), 5-13 (2160p, GPU frames of 12-22 ms at low
  clocks).
- The 1080p run in p3b has a 1.6 s gap at 45 s where DXGI's frame statistics froze while the game kept presenting
  every 16.7 ms. The baseline 1080p run has no such gap. External, not reproduced.

### What 2 ms means here
- GPU: reachable (well under 1 ms at 1080p) only when the GPU runs above idle clocks.
- Render thread: 0.4 ms, already there.
- Game thread: 3.8 ms of real work per frame, with no hotspot. Reaching 2 ms needs the translated code itself to get
  ~2x faster (code generation), or the audio mix (0.44 ms) and other runtime work moved off the game thread.

## Input latency (2026-11-04)

### The path, as the code runs it
1. **Device poll (host).** Port 0 = keyboard level (the window's own key messages, `g_key_held`, host_window.cpp) combined
   with XInput user 0; ports 1-3 = XInput users 1-3 (`gekko::poll_xinput_controller`, xinput_pad.cpp).
   **Before:** polled once per UI-loop pass on the present thread (`shadow_main.cpp`, just before
   `lifted_render.present_newest`), which waits on the swap chain: one poll per displayed frame (~16.7 ms).
2. **Latch (game thread).** Every 5 ms of game time the host service copies the published samples into the native
   peripheral layer (`ManagerImpPc::latch`; a tape replaces them), traced as InputLatch.
3. **Game read.** Once per game frame the engine calls the platform read, which is native: the lowered site at
   **0x8040EA68** (`ManagerImp::Read`) -> `ManagerImpPc::read` (the other lowered input sites: GetPortCount 0x8040E960, GetStickRange 0x8040EB38;
   tests/lift_sites_reference_tests.cpp). Held / pressed / released and stick
   normalisation are the game's own logic (translated, not interpreted; the peripheral manager around
   fn_8040EBBC), then `Player::Control::UserInput` and the behaviours. No interpreted PowerPC and no GameCube SI /
   PAD code is on this path any more.
4. **Simulation -> packet push -> hold -> record -> GPU -> present -> vblank** (frame_telemetry_report.py).

### Measured stages before (1080p, Westopolis replay; ms, p50 / p99)
- Sample age at latch: 4.6-10.6 / 16.0-16.4 (max 18.2; 33 ms at 2160p). Not part of "latch -> vblank".
- Hold (packet pushed -> recording begins): 1.6 to 14.9 ms p50 depending on the boot - where the game's step lands
  against the present thread is fixed at boot and drifts 8.93 ppm (a whole refresh every ~31 min,
  TIMING_ARCHITECTURE.md 7). This is the run-to-run and over-time fluctuation.
- Simulation (latch -> push) 3.6 / 7.2, render thread 0.3-0.4, GPU 4.6 / 7.9 (idle clocks), GPU end -> vblank
  11.6 / 16, 0 whole refreshes of queueing (no render-ahead frame; 1 refresh held per present).

### Fix 1: input thread (new, GEKKO_INPUT_THREAD=1, default off)
- A `std::jthread` "input-poll" polls XInput every 1 ms (high-resolution waitable timer) and publishes all four
  ports, merging the keyboard level the UI thread publishes (`HostWindow::keyboard_controller`, new). The UI thread
  no longer polls XInput when it is on. The latch now records when its sample was polled (InputLatch d).
- Gameplay identity: headless 40 s tape replay, `--state-report` (memory digests included) off vs on: identical.
  (Replays use the tape at the latch, so the thread cannot change a replay.)
- A/B, 1080p, alternating (.build/perf/inputab/): sample age at latch p50 10.57 / 4.63 -> 0.51 / 0.51 ms, p99
  16.0 / 16.4 -> 1.62 / 1.65 ms, max 16.5 / 18.2 -> 2.5 / 3.7 ms. Game step and repeats unchanged within noise.
- Cost: 0.54-0.58% of one core, ~680 wakes/s; process CPU 0.18-0.20 cores in both arms.
- Limitation: the keyboard level still updates when the UI thread pumps window messages (once per displayed frame).
  A keyboard press therefore still waits up to ~16.7 ms; a gamepad press no longer does. Raw Input on the input
  thread would fix the keyboard too (not done).

### Fix 2: phase lock (existing SHADOW_PHASE_LOCK=1, default off; byte-identical, TIMING_ARCHITECTURE.md 8)
A/B with the input thread on (.build/perf/lockab/), latch -> vblank p50 / p99:
- off: 27.0 / 30.7 (hold 6.8) and 35.1 / 38.8 (hold 14.9);
- on: 22.1 / 25.6 and 22.1 / 26.2 (hold 2.0 both).
The lock pins the hold at 2.0 ms in every run; it converges in the first ~20 s (the stage load) at <= 1 ms/s.

### What is left, largest first
1. **GPU end -> vblank, ~11.6 ms.** A frame starts right after vblank and is shown at the next one. Starting it later
   (just in time) would cut this, but only with margin for the GPU's worst frame; at idle clocks GPU p99 is 6-10 ms.
2. **GPU 4-6 ms** at idle clocks (210-500 MHz); under 1 ms at 1080p at moderate clocks (driver power policy).
3. **Simulation 3.6 / 7.2 ms**: the latch grid (every 5 ms of game time, 0-5 ms before the frame reads) plus the game
   step (~2.2 ms p90). Latching at the frame's own read would remove the grid part but changes which tape sample a
   replay sees, so recordings would need a new latch rule (not done).
4. Hold 2.0 ms (the lock's target; it could aim lower).

## Latency reduction and default readiness (2026-11-04, later)

### What changed (uncommitted; .build/watch)
- **Defaults, windowed runs only.** Each feature has an off switch:
  - input thread: env `GEKKO_INPUT_THREAD=0` or `--no-input-thread`;
  - phase lock: `SHADOW_PHASE_LOCK=0` or `--no-phase-lock`;
  - audio rate trim: `SHADOW_AUDIO_RATE_TRIM=0` or `--no-audio-rate-trim`.
  Headless runs (oracle, verification) never start the input thread, and the lock has nothing to measure there.
- **Raw keyboard** (`include/gekko/raw_keyboard.h`, `src/gekko/raw_keyboard.cpp`, new). The input thread owns a
  message-only window registered for raw keyboard input (RIDEV_INPUTSINK). It wakes on a key or on the 1 ms timer
  and publishes at once. It counts the keyboard only while the game window is in front, as before; releases made
  while another window had focus are seen, so no key sticks. If registration fails, it falls back to the UI thread's
  key level.
- **Read-time latch** (`ManagerImpPc::set_live_source`, live play only). The engine's pad read (lowered site
  0x8040EA68) takes the input thread's newest sample at the moment it reads. A tape that plays or records keeps the
  5 ms grid of game time, so recordings and replays are unchanged. Off: `GEKKO_INPUT_READ_LATCH=0`.
  - Why: latches happen every 5 ms of game time, but in wall time 0.08-14.5 ms apart (p50 4.7, p99 11.8), because
    the game runs a frame's work as a burst and then sleeps.
- **JIT frame start, opt-in only** (`--jit-present` / `SHADOW_R2_JIT=1`; `runtime/lift/render/jit_pacer.*`):
  - a vblank grid from DXGI frame statistics;
  - frame spans (start -> GPU fence completion) from a watcher thread;
  - each frame starts at the next vblank minus the lead, where the lead is the longest span of the last 600 frames
    plus 2 ms (spans that could miss any vblank are ignored);
  - the phase lock measures against the planned start (`phase_lock::kNothingMeasured` sentinel; negative holds are
    allowed).
- **Trace events** (present_trace.h): JitWait 21, FrameSpan 22, LiveInput 23; the InputLatch d field holds the
  sample's poll time.
- **Tools** (tools/perf/): latency_summary.py, key_probe.py, all_stages.sh, final_ab.sh, final_table.py;
  res_ladder.sh gained BUDGET_MS / NOTAPE / NATIVE / EXTRA.

### Remaining limits, measured
- **Waiting for the vblank**, ~11.6 ms with the defaults. Only JIT removes it; see above for when that pays.
- **GPU at idle clocks.** At 210-499 MHz the GPU reports 32-35 % utilisation (p50; 43-44 % p90), below where the
  driver boosts. The renderer submits once per frame and never holds the GPU idle on purpose: this is the driver's
  power policy on a light load. Changing it means driver settings, which this work does not touch.
- **60 Hz game frame.** The game reads input once per frame, so a press waits 0-16.7 ms (8.3 on average) for the
  next read. That is the game's own frame rate, kept as is.
- **Frame queue depth.**
  - No render-ahead frame: frame-latency waitable 1, newest-wins packet queue, 0 whole refreshes of presentation
    delay.
  - Two frame slots let the CPU record while the GPU runs, but every frame waits for the credit, so they add no
    latency.
- **Frame-time spikes.**
  - The only gameplay spikes are particle batches: 40-60 large camera-near particles, one batch 5.7-6.2 ms at
    2160p with 4x MSAA into a 16-bit target.
  - They arrive while the GPU is at low clocks, around 16-20 s into the Westopolis replay.
  - Real fill cost of the original effect; no cheaper target without a quality change.
- **Physical input-to-display latency** (display processing, pad radio / USB) is not measured: no camera or
  photodiode. Every number here is software, from the latch or key event to the vblank DXGI reports.

## Shared phase controller and two-lead JIT (2026-11-04, after Astra's review)

Astra's recommendation: one controller for the game's wall-time phase; a fast render-start adjustment that may spend the
packet's hold; requested lead kept apart from the lead actually available. Implemented, in Astra's order. The
controller came first, the estimator second.

### Measured first: watcher delay
The fence watcher sees GPU completion 0.12 ms p50 / 0.30 ms p99 / 0.61 ms max after the GPU's own end timestamp
(.build/perf/jitab3/). It inflates the lead by ~0.2 ms. Not the cause of the tails, so always-on GPU timestamp
queries were not added.

### The shared phase controller (gekko/phase_lock.h; the default phase lock from now on)
- **The old law:** a step of 0.001 x hold error per 1/300 s tick has a ~3.3 s time constant. It also chases an error
  that lags the shift it has already applied.
- **The new law:**
  - every packet carries the anchor shift applied when it was pushed (FramePacket::anchor_shift_ns;
    render::phase_anchor_shift_ns, written by the game thread);
  - each hold measurement becomes a target shift = shift at push + (hold - 2 ms);
  - the median of the last 31 targets is published;
  - the game thread moves straight towards it at the 1000 ppm slew limit, with a 100 us deadband.
  There is no proportional tail and no lag overshoot.
- **Off switch:** SHADOW_PHASE_LOCK_LEGACY=1 restores the old law, for A/B runs.
- **Trace:** PhaseLock d = the target shift.

### The two leads (render/jit_pacer.cpp update_lead; JIT stays opt-in)
- **Committed lead:**
  - Q99 of the last 600 ordinary spans + 2 ms;
  - rises at once only on a confirmed shift: 3 of the last 8 spans above the frozen reference Q99 by 0.75 ms, or the
    median of the last 16 above the reference median by max(1 ms, 25 %); it then goes to at least Q90(last 16) +
    2 ms, held 120 frames;
  - falls only after 600 clean frames, at most 0.25 ms per second.
  The phase lock is measured against the vblank minus the committed lead.
- **Risk lead:** the committed lead, or a transient (span + 2 ms) that lasts until 30 clean frames. The frame starts at
  the vblank minus the risk lead, so a burst spends the packet's hold and never moves the game.
- **Overload spans** (>= period - 1 ms) raise the transient but stay out of the Q99 history.
  - This deviates from Astra, which keeps them in the history.
  - No lead helps such a frame, and counting it would switch JIT off for minutes after a burst.
- **Wrap guard:** a hold sample is kept within half a period of the target. The first JIT A/B showed the target
  jumping by a whole frame (17.7 -> 33.9 -> 10.5 ms) when a frame started after its vblank. With the committed lead
  stable, real errors stay far below half a period.
- **Uncovered demand** (requested lead the frame did not get) is traced per frame (JitWait d) and reported.

## GPU burst prediction (2026-11-04, experimental; nothing default)

Brief: identify the stage-start bursts, reduce them where possible, then test whether CPU-visible prediction fixes the
scheduling that remains. The phase controller was not touched; JIT stays opt-in; every new path is off by default.

### 1. What the bursts are (.build/perf/burst1/, 1080p, GPU trace + per-draw trace + NVML clocks)
- **Where:** 48 frames over 7 ms between packets 1149 and 1202 (about 19-20 s into the Westopolis replay).
  - The scene pass is 8.1 ms on average in those frames; every other pass is under 0.5 ms.
  - Inside the scene pass: particle batches 6.31 ms per frame, meshes 1.74 ms, immediates 0.03 ms.
  - One effect does it: texture handle 16777457 accounts for 6.17 ms per heavy frame.
- **Load:** the median particle count is 1,968 in heavy frames against 729 in normal ones.
- **Clock:** the GPU sits at its 210 MHz idle clock through the burst, which lasts about a second - too short for the
  driver to boost.
- **Reducing the workload:** the cost is fill, large blended quads into the 4x MSAA R16G16B16A16 scene.
  - Every cheaper option changes the output: a lower-precision target, no MSAA for particles, a lower resolution.
  - One output-identical candidate is open: trim each quad to its texture's visible region, keeping a one-texel
    filter margin, so pixels the shader discards anyway are never rasterised. Not done; it needs a per-texture
    alpha-bounds pass.

### 3. The scheduling ceiling, measured before building
In the JIT schedule a packet arrives about one hold (2 ms) before its planned start, so a prediction made from the
packet can move its start earlier by at most that hold. The two gameplay repeats of each earlier 1080p JIT run

- **Packet 94 (boot):** span 9.8-10.2 ms against a 9.7-9.8 ms available lead, with the packet 12-23 ms early. An
  early start would have saved it.
- **Packets 1187 / 1189 (the burst):** span 14.2-14.3 ms. The reactive transient already asked for 15.8-16.0 ms, but
  the packet only arrived 13.9-14.3 ms before the vblank. No start choice can save it.

### 4. The experiment (SHADOW_R2_JIT_ASSIST, off by default; render/jit_pacer.cpp)
- **predict:** the newest packet's fill is estimated before its start is chosen (PacketQueue::with_newest). The
  watcher thread fits the online model (update_model) from the fences it already waits on. When predicted span +
  allowance + margin exceeds the risk lead, the frame starts at once instead of at its planned start. Trace
  JitPredict (25).
- **eager:** always start at once.
- **Why both:** a frame started earlier is shown at the same vblank with the same input, so starting early costs no
  input latency. Eager is the best case any predictor can reach.
- **Unchanged:** the phase controller still measures the hold against the planned start.

### 6. Verdict
- **Not worth pursuing in this form.** Prediction-assisted JIT does not improve on the two-lead JIT: medians within
  ~0.4 ms, the same p99 / p99.9 at 1080p and 5K, worse at 32:10, and repeats within run-to-run noise.
- **Even the eager best case does not help.** Spending the whole hold on every frame (no false alarms, nothing
  missed) does not move the tails either. The frames that miss do so because their packet arrives too late, not
  because their start was chosen badly. That matches the ceiling in section 3.
- **No stalls added:** the model costs a few thousand multiply-adds per frame (fill) and an RLS update on the watcher
  thread; no readback, no wait.
- **What would help instead:**
  1. Cut the burst's GPU cost without changing the output - the quad-trim candidate above.
  2. Hold a larger permanent reserve (more hold), costing about that much latency in every frame.
  3. Early warning before the game produces the frame (effect activation, stage events), early enough for the phase
     lock to move the game - at 1 ms per second it would need seconds of warning, which no measured signal gives.
- **JIT itself:** a net latency gain only at 2160p in these runs (-1.9 ms median, p99 equal), with more repeats there.
  It stays opt-in.
- **Stage start:** stage initialisation gives no usable early warning. The burst begins about 19 s in, at an effect's
  activation; a frame's fill rises with its packet, too late for the phase.
- **Out of scope here:** the C runtime malloc pools were not touched; profiling never showed allocation above
  0.007 ms per frame.

## Particle-trim experiment (2026-11-04): stopped at the safety check

Brief: crop the burst effect's particle quads to a conservative rectangle outside which no sample can change the
picture, but only if that rectangle removes meaningful coverage. JIT stayed off; nothing default changed.

### The effect's state (SHADOW_R2_PARTICLE_AUDIT=<csv>, new diagnostic; .build/perf/trim-audit/particles.csv)
- Texture 16777457 (0x010000F1).
- **Blend** SrcAlpha / InvSrcAlpha, **depth test on, depth write off**, **fog on**, **alpha cutoff 0** (nothing
  discarded).
- **Sampler:** anisotropic, **wrap / wrap**.
- **Colour:** per-particle colours.
- **UVs:** always (0,0)-(1,1) - no atlas frames. Rotated particles are common.
- 11,305 draws and 659,661 particles in 40 s - the largest particle user by far.
- **The neutral texel:** with this blend a fragment of final alpha 0 leaves colour and alpha exactly unchanged (fog
  changes RGB only, no depth write). So "alpha 0 across the whole filter footprint" would have been the condition for
  a texel that can be dropped.

### The texture (SHADOW_R2_DUMP_TEXTURE)
32 x 32, 6 mip levels, a soft blob. Each level's alpha > 0 bounding box, widened by the one-texel bilinear footprint:

| level | size | alpha > 0 texels | bounding box | safe UV rectangle |
|---|---|---|---|---|
| 0 | 32 x 32 | 691 of 1,024 | x 1..31, y 1..31 | whole texture (and past the edge) |
| 1 | 16 x 16 | 189 | x 0..15, y 0..15 | whole texture |
| 2-5 | 8x8 .. 1x1 | 52, 16, 4, 1 | the whole level | whole texture |

- With wrap addressing, a sample at one edge reads texels at the opposite edge, so even level 0's empty first row and
  column cannot be cut.
- **The safe rectangle is the full quad at every reachable level: 0 % removable coverage.**
- Per the brief, the experiment stops here. No prototype was built.
- A non-rectangular crop could remove at most the ~33 % fully transparent texels of level 0, with the wrap and filter
  problems unsolved. Out of scope for this bounded experiment.

### Consequence
- The particle burst's cost is real coverage of a soft, almost full-quad texture, with nothing to trim exactly.
- What remains for it, all outside this brief:
  - the GPU's idle clock;
  - a cheaper target format or no MSAA on particles, both of which change the picture;
  - accepting the occasional repeated refresh at 2160p and above.
- The current defaults are unchanged.

## CPU and GPU weak spots (2026-11-04, current build, defaults, 1080p Westopolis replay; .build/perf/weak/)

### CPU: game thread 3.91 ms of work per frame (external RIP sampler, 60 s)
- **Translated game code: 2.32 ms.** Spread over thousands of functions; the largest is 0.07 ms.
- **Audio on the game thread: 0.33 ms** (AX mix, voices, reverb, ADPCM). The largest non-game item.
- **CPU dispatch: 0.31 ms.** find_hle 0.074, try_hle_slow 0.040, Cpu::run 0.038, lift sites 0.035, call_indirect
  0.033, indirect_call_trace::enabled 0.017, find_range 0.015.
  - **The trace check:** indirect_call_trace::enabled() is an out-of-line call with two static guards on every
    translated indirect call. An inline flag would remove it.
  - **The HLE filter:** 1,024 slots; 32 of 248 hooked slots are shared. Most of find_hle's time is genuine hook
    dispatch (for example the object-range hook, about 1,000 hits per frame).
- **Native intrinsics: 0.21 ms** (matrix, collision, math). Real work.
- **Interrupts / timing: ~0.1 ms.**
- **PPC helper calls: 0.11 ms** (fp_compare 0.046, paired-single load/store 0.045).
- **Guest memory accessors: 0.10 ms.**
- **C runtime: 0.09 ms**, including printf formatting 0.013 ms on the game thread every frame. Its caller is not
  identified: the sampler records the leaf only.
- **Render packet build: 0.08 ms.**

### CPU: present / render thread 0.42 ms per frame
Mostly the NVIDIA driver and D3D submission. No weak spot.

### GPU: 4.16 ms per frame at 1080p, 5.64 ms at 2160p
- **No idle gaps:** the passes add up to the whole frame.
- **Clocks** (NVML): the core sits at about 210 MHz (64-94 % of samples), the memory at 405 MHz (44-95 %, maximum
  11,201 MHz), at 34-43 W.
- **Pass shares, 1080p / 2160p:**
  - scene 67 % / 64 %;
  - compose 12 % (0.51 ms) / 5.5 %;
  - resolve 6 % / 10.5 %;
  - glare composite 4 % / 8.4 %;
  - glare chain ~8 %;
  - present scale - / 1.9 %.
- **What that means:** at these clocks the full-screen passes are memory-bandwidth-bound. Compose (a point-sampled
  copy into the output) costs twice the 4x MSAA resolve at 1080p.

### Ranked weak spots and what fixing each would take
1. **GPU idle power state** (core and memory). Biggest lever; a driver setting, so not changed.
2. **Full-screen memory traffic.**
   - Compose as a separate copy: about 12 % of the 1080p GPU frame. Resolving the single view straight into the
     output would remove one full-screen read + write.
   - Risk: the 16-bit intermediate disappears, so rounding may differ - this needs a pixel-exact check.
   - The resolved view is also read later (heat haze, motion trail).
3. **Audio mixing on the game thread** (0.33 ms per frame): an architectural move to the audio thread.
4. **Dispatch overhead** (~0.3 ms): small items. An inline trace flag is trivial; the HLE filter size is a cache
   trade-off.
5. **printf on the game thread** (0.013 ms): find the caller (stack sampling) and remove it.

## Weak-spot survey and fixes (2026-11-04, evening)

Five read-only Sonnet 5.5 agents surveyed one area each: dispatch, audio on the game thread, GPU full-screen passes,
per-frame host work, and the render packet build. Their findings were checked against the code before anything was
changed. Everything below is uncommitted.

### Fixed (default on, exact)
- **find_hle** (cpu.cpp):
  - Any filter slot other than kHleSlotAll now proves an address unhooked, so the unhooked answer skips the hash.
  - The filter grew from 1,024 to 4,096 slots (16 KiB).
  - A shared slot scans its few hooks instead of hashing.
  - Verification and a latched fault still fill every slot and use the map.
- **Indirect-call trace flag** (indirect_call_trace.h): an inline load of a flag set before main, replacing an
  out-of-line call with two guarded statics on every translated indirect call.
- **Lift-site check** (cpu.h / cpu.cpp): an exact 8,192-bit filter before the binary search over ~1,050 sites that ran
  on every dispatch iteration.
- **AX parameter blocks** (system.cpp AxPbView): ~70 GuestMemory::read16 calls per voice per 5 ms frame became one
  resolved pointer.
  - The block is proven mapped by select_ax_parameter_blocks; the advance's own write16s are seen by later reads.
- **Interrupt priority** (native_interrupts.cpp best_pending): the priority table (up to 32 guest reads per source)
  is read only when two sources compete. A single candidate wins outright.
- **The game thread's printf** (rw_driver pipelines.cpp): found.
  - The deform audit formatted a text on every skinned and morphed draw, which deform_report then discarded after the
    first report.
  - The text is now built only when it will print (deform_unreported).
- **Reverb** (lift/audio/reverb.cpp): the subnormal mode is a template parameter and the helpers are force-inlined.
  The arithmetic is unchanged, including the double forms.
- **Mixer SRC window** (native_audio_mixer.cpp): the linear SRC reads a flat history+source+silence copy instead of
  two range tests per tap. Voices reaching past 1,028 samples keep the old path.
- **Compose clear** (renderer.cpp): when one view covers the whole output, the output is discarded, not cleared. Its
  opaque copy overwrites every pixel.

### Validation
- **Identity, three captures:** headless Westopolis tape replays, captures at 15 s and 25 s (1080p) plus 2160p
  scaled to 1080p, with --state-report and --audio-dump. Baseline binary against final:
  - 0 of 2,073,600 pixels differ;
  - audio PCM byte-identical;
  - state report identical, memory digests included.
  - Runs: .build/perf/ident/.
- **Tests:** axfx_reverb_contract_tests (oracle against the game's own reverb words, both subnormal modes) and
  native_audio_mixer_tests pass.
- **38-stage live boot sweep** (final build, .build/perf/all-stages-weakfix.log): 38 / 38 PASS, clean.

### Measured (external sampler, 60 s of 1080p gameplay, two runs per side, ms per frame; .build/perf/weakfix-prof/)
- find_hle 0.064 -> 0.027
- GuestMemory::read16 0.041 -> 0.004
- run_lift_site_at_pc 0.040 -> 0.012
- indirect_call_trace::enabled 0.019 -> 0 (call_indirect +0.006, now inlined)
- GuestMemory::peek32 0.0085 -> 0.002; best_pending 0.009 -> 0.005
- render_voice 0.059 -> 0.048
- Reverb total 0.103 -> ~0.10. Inlining barely helps: the kernel is arithmetic-bound.
- **Game-thread total: 3.83 -> 3.81 ms.**
  - The function-level savings add up to about 0.15 ms.
  - Run-to-run noise in the total is of the same size, so no total gain is claimed.
  - The game thread is guest code; the dispatch overhead was never large.

### Tried, NOT made default: direct resolve (SHADOW_R2_DIRECT_RESOLVE=1, opt-in)
- **The idea:** the one full-output view resolves straight into the 8-bit output; compose and the 16-bit view
  texture are skipped.
- **GPU gain:** frame p50 3.92 -> 2.78 ms at 1080p (two fullscreen runs each, .build/perf/weakfix/). That is -1.1 ms,
  about 29 %, more than compose's 0.51 ms: at the idle memory clock the whole 8 B/px round trip goes.
- **Not bit-exact:**
  - 88 and 216 of 2,073,600 pixels are one 8-bit step high, all +1.
  - That is with the 16-bit step emulated by exact round-to-nearest of the true product.
  - Plain float rounding gave 102 and 249.
- **Cause:** the GPU's float -> UNORM16 store is not round-to-nearest (D3D allows 0.6 ULP). The 16-bit intermediate
  IS that store, and no vendor-independent shader expression reproduces it.
- **Precedent:** the B3a glare fold was accepted with ~11 pixels per frame one step off. This is the same class of
  difference, but larger (~0.01 % of pixels). Making it default is the user's call.

### Not done (with reasons)
- **The audio mix on a worker thread** (~0.2 ms): architectural. It would need a join before the sink, savestates
  and the reverb callback, and guest-memory writes from another thread.
- **The paired-single generic fallback** (psq_load / psq_store 0.02-0.045): would need the recompiler's --psq-sites
  list extended.
- **Renderer::record per-frame maps / vectors:** <=0.01 ms.
- **RwDriver::reconcile sweep:** not exact (delays handle release).

## Bug hunt (2026-11-04, night)

Four read-only Sonnet 5.5 agents each hunted one area: the input thread, frame pacing, today's dispatch and audio
edits, and the renderer / frame graph. Every finding was checked in the code before a fix. All fixes are
uncommitted.

### Recompiler / native owners
- **DCInvalidateRange (0x80372508) and DCFlushRangeNoSync (0x80372594)** were still translated: an empty counted loop
  per 32-byte line, with a dispatch test on every back edge. The AX frame ran them over its buffers (0.062 ms/frame).
  Their two siblings with `sc` were already owned.
  - They are now native owners (extract/native-owners.txt, so ppcrecomp emits only a thunk). The loop heads
    0x80372524 / 0x803725B0 are owner entries, so a resumption mid-loop still works.
  - Stricter than the existing cache owners: the owner leaves exactly the registers the loop leaves (r3, r4, r5, CTR,
    CR0) - game_memory.cpp serve_cache_range_loop / _resume.
  - Proof: cache_range_owner_tests runs the ORIGINAL words in the reference interpreter. 73,224 register checks,
    0 failures: every alignment, line edges, random ranges, address wrap and loop-head resumes.
- **find_hle hardening:** an address equal to a slot sentinel (1 or 3) could index the bucket table out of bounds.
  Unreachable for a word-aligned pc, but now refused.

### Input thread (real bugs, fixed)
- **Dead keyboard without a high-resolution timer** (Windows before 10 1803, or a failed create): the raw-input
  messages were never pumped, so the keyboard was dead for the whole run. The fallback now pumps.
- **Stuck key:** a key released while the raw sink saw nothing (secure desktop: Win+L / UAC; an elevated window in
  front) stayed held when the game came back to the front. RawKeyboard::resync() clears keys the system no longer
  reports down, on every return to the foreground.
- **Fake Shift:** with NumLock on, the grey arrow keys arrive wrapped in E0 2A / E0 36 fake Shifts. Raw input reports
  them as VK_SHIFT (the window path never saw them), so Enter + an arrow briefly read as Shift+Enter = Start. Now
  ignored.

### Renderer (real bugs, fixed)
- **resize_window** cleared the whole target pool before the swap chain's same-size check. Every repeated WM_SIZE
  (restore / maximise without a change) threw away every placed target - hundreds of MiB at 5K - and reallocated them.
  A same size now returns at once.
- **A failed ResizeBuffers** left the back buffers released and the old size cached. Every later resize to that size
  returned early, and record() drew into a null output, which is the off-screen capture path. The result was a
  silently frozen window. Now:
  - the size is forgotten on failure, so the next resize retries;
  - render() fails the frame when there is no back buffer.
- **Device lost** (TDR, driver reset): Present failed silently, every frame. The cause (GetDeviceRemovedReason) is
  now reported once on stderr. Recreating the device is not implemented; that is a larger design.
- **Glare fold span bounds:** a far canvas vertex converted to a 32-bit long out of range, skipping the draw's tiles.
  Now clamped in double first; identical within the view.
- **Direct resolve (opt-in):** two missing guards added - a 16-bit scene format, and the pipelines existing (there is
  no compose after it to cover a failed one).

### JIT pacer (opt-in, fixed)
- **Hold sampling:** with JIT requested, frames it did not plan (no grid yet, a resize, a refresh re-base) are no
  longer sampled. Their hold used a different reference and could flip the target median by ~8-12 ms.
- **Implausible frame statistics** (period outside 1-100 ms) restart the grid. A zero period would divide by zero; a
  tiny one would make the wrap loops run for millions of steps.
- **A fence wait that cannot be set up** drops the span instead of recording a too-short one.

## Recompiler: where translated code spends its time (2026-11-04, late)

### A cost breakdown by what the generator emits
- **New tool:** tools/perf/sample_threads.py SAMPLE_LINES=1 maps every game-thread sample in translated code to its
  generated source line (PDB line tables).
- **Classification:** a classifier (scratch: codegen_classes.py) groups the lines by the construct emitted.
- **Totals:** translated code is 2.34 ms of the 3.8 ms game thread, spread over ~3,000 functions (none above
  0.14 ms).

1080p Westopolis, 60 s, ms/frame, before the thunk change:
- 0.444 GPR arithmetic (register loads and stores in the Cpu object)
- 0.411 entry thunks: `void fn_X(Cpu& c) { if (c.try_hle(X)) return; fn_X_body(c, X); }`
- 0.253 CR updates / compares
- 0.246 memory reads; 0.074 memory writes
- 0.236 float loads / stores (single <-> double)
- 0.228 FP arithmetic helpers (already inline fast paths)
- 0.099 call epilogues (exiting / finish_transfers / pc != link)
- 0.016 loop back-edge dispatch tests; 0.024 FP-available tests; psq 0.001

### Fix: frameless entry thunks (generator + cpu.h)
- **Before:** the thunk saved a register and adjusted the stack on EVERY call (push rbx / sub rsp / ... / pop rbx). The
  only reason was that its rare slow path, try_hle_slow, was a call in the middle.
- **Now:** `if (c.hle_clear(X)) return fn_X_body(c, X); c.enter_slow(X, &fn_X_body);`.
  - Both arms are tail calls.
  - The hot path is mov / cmp / je / cmp / je / mov / jmp, with no frame.
  - hle_clear is exactly try_hle's filter; enter_slow is `if (!try_hle_slow(X)) body(c, X)`. Same order and checks,
    in every mode (verify / fault fill every slot, so enter_slow).
- **Measured:** thunk line 0.411 -> 0.32 ms/frame; translated code 2.34 -> 2.15 ms/frame (two runs: 2.148 / 2.149).
- **Proof:**
  - ppcrecomp_output_structure passes;
  - state and audio identical at 15 s and 25 s;
  - pixels identical to a fresh baseline run (the baseline itself shows one 1-LSB MSAA pixel run to run);
  - 38 / 38 stages.

### What is left, and why it is one structural thing
- **The common cause:** GPR arithmetic, CR updates, register moves and reloads after stores all come from one fact.
  Guest registers live in the Cpu object, and MSVC has no type-based alias analysis. So after every guest memory
  store (a u32 store through a pointer) it reloads every register it needs, and CR can never stay in a host
  register.
- **The fix:** register promotion in the generator.
  - Keep the GPRs / CR a function uses in C++ locals.
  - Write them back at every observation point: call, return, yield, indirect branch, lift site, helper that reads
    state, and a potential fault.
  - Reload after.
- **Estimate:** the affected classes are ~0.75 ms of the 2.15 ms. A realistic win is 0.3-0.6 ms/frame of the game
  thread.
- **Risk:** it touches every instruction emitter and the fault / verification contracts. It needs its own validation
  plan: the verify-recomp oracle on every function class, then identity runs. A separate project.

### The direct resolve, now exact: a measured conversion table (unorm_calibration.cpp)
- **The idea** (Astra's "calibrate the final thresholds"): the compose chain F(m) = byte, through the R16
  render-target store, point compose and 8-bit store, is nondecreasing. So it is fixed by 255 thresholds per channel.
  They are MEASURED once at start-up on the running device, through the same pipelines, formats and sampler:
  - g(v): the compose byte for all 65,536 R16 codes. It must be a nondecreasing unit-step map, 0 -> 0, 65535 -> 255.
  - For each byte k: a float bracket one code either side of the code where g reaches k, narrowed by repeated
    passes (1,024 evenly spaced floats per bracket per pass, stored through the R16 render-target store, read back,
    mapped through g) until its ends are adjacent floats. Monotonicity and containment are checked every pass.
  - Checks:
    - every representative k / 255 must store as byte k;
    - every threshold must lie within 0.1 step of (k - 0.5) / 255.
    Any failure leaves the compose path running.
- **The shader** (direct_byte, utility.hlsl / glare.hlsl):
  - s = m * 255 + 0.5, k = floor(s).
  - If s is more than 0.125 of a step from a boundary, the byte is k with no table read. That is proven by the
    0.1-step bound plus a 0.025 margin.
  - Otherwise one table read decides between two neighbours. Most pixels read nothing.
- **What the table shows about this GPU:**
  - The R16 store's transitions sit at x * 65535 = v - 0.5 + delta, with delta ~0.06 near 0 falling to ~0.002 near 1:
    not round-to-nearest, slightly low.
  - The 8-bit store of the composed value steps at R16 code 256k - 112, not 257k - 128.5.
  - All four channels are identical. Diagnostic dump: SHADOW_R2_UNORM_TABLE=<file>.
- **Identity:**
  - The direct resolve against the compose path, same binary, at 15 s and 25 s (1080p) and 2160p -> 1080p:
    0 pixels differ, except pixel (837,375) at 15 s.
  - That pixel's blue channel is 185 or 186 run to run on the compose path ITSELF (baseline, bug-fix and thunk
    builds show both). The direct resolve gives 185, one of the compose path's own outcomes.
  - Audio and state identical.
- **GPU, fullscreen, two runs each, frame p50:**
  - 1080p native: 3.60 / 3.58 -> 2.91 / 2.94 ms (-0.66 ms, -18 %).
  - 2160p rendered into the 1080p window: 5.64 / 5.63 -> 5.71 / 5.66 ms (no gain; there the compose was small and the
    classification's ALU at the idle core clock costs as much).
  - The first table version (up to four table reads per channel) was slower at 2160p; the boundary-only read fixed
    the 1080p gain, not the scaled case.
- **Default:** SHADOW_R2_DIRECT_RESOLVE unset = the direct resolve when the render size is the output's; 1 = also

### Audio lifecycle (gekko/schedule_offset.h; audio_runtime.cpp)
